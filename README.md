## 1. 需求概述

### 1.1 需求背景

一份 PRD 的平均寿命是两次评审。第一次评审，大家讨论它；第二次评审，大家讨论为什么没人按它做。

本 skill 不打算改变这个事实，只打算让这两次评审短一点。

目前的 PRD 主要有三种死法：

1. **死于正确**
   a. "本模块旨在为用户提供全面、高效、智能的解决方案"
   b. 每个字都对，合起来什么也没说
2. **死于详尽**
   a. 第 47 页有一段 JSON 示例
   b. 它会比这个项目活得更久
3. **死于勇敢**
   a. "预计提升效率 50%"
   b. 写下这个数字的人后来很少再写数字
4. **死于 AI**
   a. 格式完美，语气礼貌，每一节结尾都有一段"综上所述"
   b. 生成用了十秒，没有人读完。包括让 AI 生成它的那个人

为什么值得做：
- **文档是项目留下来的唯一证据。** 需求会变，人会走，Demo 会过期。最后能回答"当时为什么这么做"的，只有一份写得诚实的文档。所以它应该写得像证词，而不是像宣传册。
- **"本来真不想写"是一种工作态度。** 不情愿的人写得克制。克制的人写"本期不做"。写"本期不做"的人，项目通常能活过 Phase 2。
- **AI 写的文档没人看，这一份例外。** AI 写文档的问题从来不是写得不够多，而是写得太像 AI：每个观点都"值得注意"，每个方案都"兼顾了灵活性与可扩展性"，每一段都在总结上一段。本 skill 由 AI 执行，但禁止它写得像 AI。你读到这里，说明它做到了。
- **结构和表达都有出处。** 结构参考了一套我们没法公开名字的 PRD；表达规则参考了 [ste-clarity](https://github.com/yfHHHE/ste-clarity) 的中文部分。前者教我们怎么组织，后者教我们怎么不撒谎。

### 1.2 产品路线

| 阶段 | 核心 | 预期结果 |
|---|---|---|
| **Phase 1（本期）** | 写出一份读得懂的 PRD | 评审时间缩短 |
| Phase 2 | 写出一份没人能挑毛病的 PRD | 评审取消，因为没人读 |
| Phase 3 | 写出一份不需要存在的 PRD | **[愿景]** |

每个阶段都以上一个阶段的幸存为前提。

|---|---|---|---|

## 2. 各模块详情

具体用法见 [`SKILL.md`](skills/benlai-zhen-buxiang-xie/SKILL.md)。

### 2.1 优先级

| 模块 | 功能 | 优先级 |
|---|---|---|
| 结构模板 | 提供一副骨架。骨架不会让文档变好，但能让它站着 | P0 |
| 语气与写法 | 让文档听起来像一个人写的，而且这个人愿意为它负责 | P0 |
| 中文清晰度 | 让"应当"保持"应当"，让"暂未发现"保持"暂未发现" | P0 |
| 发出前检查 | 四道关。比起写得好，更重要的是不出事 | P0 |
| 交付到飞书 | 放进飞书，并且不覆盖你的修改。这一条规则是付过代价才写下的 | P1 |
| 帮你说服别人 | — | 本期不做。文档能做的只有写清楚 |

### 2.2 结构模板

业务实体：PRD

| 字段 | 说明 |
|---|---|
| 开场白 | 1–3 句。承认你本来不想写，这是全文唯一不需要证据的部分 |
| 需求概述 | 一屏以内。第二屏开始，读者数量呈指数下降 |
| 各模块详情 | 实体、流程、特别注意。三样都有，才算想清楚了 |
| 本期不做 | 全文被引用次数最多的一节 |
| 验收标准 | 端到端。写不出验收标准的需求，通常也做不出来 |
| 待确认事项 | 项目的遗嘱。写得越早，纠纷越少 |

特别注意：
- 模块标题写目的，不写动作。「订单模块：让用户一眼找到卡住的订单」是一个目标；「订单模块优化」是一种心情。
- 编号连续，不重复。两个「需求概述」意味着这份文档被两个人改过，而他们没有说过话。

### 2.3 语气与写法

第一人称，有判断，敢砍需求。

| 不像 | 像 |
|---|---|
| 本模块旨在赋能用户、打通链路、形成闭环。 | 这期就做一件事：让用户一眼找到卡住的订单。 |
| 可考虑后续迭代中持续优化。 | 这块先不做，放到 Phase 3。 |
| 根据相关领导的指示…… | （直接写成产品决定。决定比人活得久） |
| 预计提升效率 50%。 | 收益阈值拿到基线后再定。 |
| 打造行业领先的智能化平台。 | （删除。没有人会因为删了这句而难过） |
| 值得注意的是，该方案在兼顾灵活性的同时，也充分考虑了可扩展性。 | （删除。这是 AI 在思考下一句写什么时发出的声音） |

特别注意：
- 比喻一句就够。"上期埋入 AI 的基因，这期塑造骨骼"，这是定位。再往下写"下期长出肌肉"，就成了尸检报告的反面。
- 可以口语，不可以轻浮。文档会被截图，截图没有上下文。

### 2.4 中文清晰度

改编自 [ste-clarity](https://github.com/yfHHHE/ste-clarity) 的中文部分。

- **必须、应当、可以**是三个不同的词。混用它们的文档，最后会在会议上被逐字朗读。
- **"基本完成"不等于"完成"。** 两者之间的距离，通常是一个季度。
- **没有数据，就不画趋势。** 拿不到的数写"暂不可用"，不写 0，也不写"没有异常"。0 是一个数，"没有异常"是一个承诺。你可能两样都给不起。

### 2.5 发出前检查

1. **内容可信**：没有编的数字、编的负责人、编的原因
2. **可以给别人看**：没有名字，没有内部规则，没有能认出你们是谁的细节
3. **范围克制**：MVP 不包含愿景
4. **写法**：有开场白，有「本期不做」，编号不重复

四关全过再发。发之前确认已经打开分享权限。否则第一条回复会是"没权限"，第二条会是"我也是"。

### 2.6 本期不做

- **让人读完。** 我们只负责让读到的部分是对的。
- **v1.0。** 见作者一栏。
- **把愿景写进 MVP。** 试过一次。用户的评价是"有点激进"。我们把这个评价写进了规则，没有写进简历。
- **点名。** 文档会存在很久，比大多数合作关系都久。

## 4. 验收标准

以下验收以完整流程为单位，每条要端到端跑通才算通过。

### AC-1：写出来

前提：用户有一个 Demo，和一个不得不写的理由
1. 用户说"本来真不想写"
2. skill 先复述用户的思路，提 2–4 个问题，不急着动笔
3. 用户拍板后，产出一份结构完整的 PRD
4. 用户读完开场白，没有想改

### AC-2：不留证据

1. 全文搜索同事的名字，结果为 0
2. 全文搜索"赋能""抓手""一站式"，结果为 0
3. 全文搜索"提升 50%"，结果为 0
4. 全文搜索"值得注意的是""综上所述""总而言之"，结果为 0。这三个词出现的地方，就是读者离开的地方

### AC-3：不越界

1. MVP 里没有愿景
2. 面向客户的内容里没有内部规则
3. 用户说"先别改"，文件确实没变

### AC-4：活过评审

1. PRD 发到群里
2. 有人回复"清楚"
3. 没有人问"这个是谁定的"

## 6. 愿景

我们相信，总有一天，每一份 PRD 都会以一句诚实的话开头。

那时，"必须"就是必须，"暂未发现"就是暂未发现。研发打开文档，先看「本期不做」，然后安心地去做剩下的部分。评审会准时结束。没有人问是谁定的，因为文档里写着为什么。

这一天大概不会到来。但愿景本来就不是用来到来的。它是用来让 Phase 1 看起来有意义的。
