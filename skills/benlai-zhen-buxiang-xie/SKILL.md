# 本来真不想写

> 本来真不想写 PRD 的，Demo 比文档清楚。但项目不是一个人的项目，没有一份文档把边界和流程讲清楚，最后一定是各做各的。所以还是写一份。

这个 skill 帮用户写出**读起来像人写的、能直接拿去对齐的**中文 PRD：结构稳定、语气坦诚、只写有依据的内容，细节刚好够各方对齐，不写成技术设计书。

## 什么时候用

- 用户要写、改、审 PRD、需求文档、产品方案、分期规划
- 用户给了 Demo、聊天记录、代码、调研材料，要整理成需求文档
- 用户说「本来真不想写」

## 工作流程

1. **先读材料，再动笔。** 读用户给的 Demo、聊天、代码、旧文档。分清四类信息：已决定的、用户的想法、别人的意见、还没定的。
2. **先讨论，再成文。** 涉及方向、MVP 范围、分期时，先用几句话复述用户的思路，指出可以改进的地方，问 2–4 个会改变文档走向的问题。用户拍板后再写。
3. **MVP 要克制。** 最好的理念放在「愿景」里，MVP 从最基础、风险最低、能用真实数据跑通的地方出发。每个阶段以上一阶段建立的信任为前提，不跳级。
4. **按骨架写**，见 [结构模板](references/structure.md)。
5. **用作者的口吻写**，见 [语气与写法](references/voice.md)。
6. **做一遍清晰度检查**，见 [中文清晰度规则](references/clarity-zh.md)。
7. **发出前过一遍清单**，见 [发出前检查](references/checklist.md)。
8. **交付**：默认写成本地 Markdown。要放进飞书时，按 [交付到飞书](references/lark-delivery.md) 处理。

## 核心规则

1. **交互以 Demo 为准，PRD 写业务。** PRD 描述业务实体、实体关系、依赖这些实体运转的业务流程，以及本期做什么、不做什么。不写像素级 UI，不写成技术设计书。
2. **细节到"能对齐"为止。** 写原则、实体、流程、边界和验收；不写 JSON 示例、合并算法、完整字段清单、逐个组件的实现细节。需要时指向 Demo 或技术方案文档。
3. **只写有依据的。** 不编数字、指标、负责人、时间、原因、趋势。没定的标 **[待确认]**，设计建议标 **[提案]**，不当作结论。
4. **不点名。** 文档里不出现同事的名字，也不写"按某人的安排""某人说"。分工只写"部分 + 说明"，必要时写团队或角色。作者一行可以保留用户自己的名字。
5. **敏感业务信息泛化。** 具体的合作方、地区、内部计划、客户名等，改成"某个合作方""某个业务主体"这类说法，除非用户明确要保留。
6. **对客户的内容要过审。** 面向客户的答疑、提示，来源必须是相关团队审核过的对外版本；不暴露内部规则、审核标准、风险阈值，不透露针对个案的内部判断原因。
7. **明确不做什么。** 每个模块都可以有「本期不做 / 放到 Phase N」，单独一节汇总。砍掉的东西说清楚去哪了。
8. **保留原意的强度。** 必须 / 应当 / 可以 / 不得 / 预计 / 暂未 这些词不随意替换。改写用户的原话时，事实、条件、否定、不确定性都要保留。

## 与用户协作

- 用户改过的文档就是最新版本。再次修改前，先读回最新内容，把用户的改动当作决定吸收进来，不要覆盖。
- 用户说"先别改"时只讨论，不动文件。
- 用户删掉的内容（比如某句商业判断、某个名字），视为偏好，后续版本同样不写。
- 每次改版，在回复里用几行说明改了什么、哪些是替用户做的决定、还有什么风险。不要在文档里写变更记录，除非用户要。
