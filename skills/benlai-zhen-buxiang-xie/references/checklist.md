# 发出前检查

## 第一关：内容可信（不通过就先改）

- [ ] 没有编造的数字、指标、负责人、时间、原因、趋势
- [ ] 没定的都标了 [待确认]，并在「待确认事项」里汇总
- [ ] 设计建议标了 [提案]，没有写成已有接口或已定方案
- [ ] 改写用户原话时，约束强度、条件、否定、不确定性没有变

## 第二关：可以给别人看

- [ ] 全文没有同事的名字，没有"按某人安排""某人说"
- [ ] 分工表和待确认表没有"负责人 / 找谁"列（除非用户要）
- [ ] 具体的合作方、地区、客户名、内部计划已泛化
- [ ] 面向客户的内容来自审核过的对外版本；没有暴露内部规则、审核标准、风险阈值、个案判断原因
- [ ] 用户之前删掉的内容没有再出现

## 第三关：范围克制

- [ ] MVP 从风险最低、能用真实数据跑通的地方出发
- [ ] 理念性、需要大量前置条件的东西放在「愿景 / 后续 Phase」
- [ ] 每个砍掉的功能都写了去向
- [ ] 涉及钱、权限等高风险动作有明确的边界

## 第四关：写法

- [ ] 有坦诚的开场白和「以 Demo 为准」的说明
- [ ] 每个模块有实体、流程、特别注意
- [ ] 细节停在"能对齐"：没有 JSON 示例、算法细节、完整字段清单
- [ ] 验收标准以端到端业务流程为单位，有前提、有步骤
- [ ] 章节编号连续、不重复；术语全文统一
