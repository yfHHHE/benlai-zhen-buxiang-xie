# 结构模板

章节编号连续、不重复，不要出现两个「需求概述」或重复的小节编号。按需取舍，不是每节都必须有。

```markdown
# 【项目名】Phase N / MVP：一句话定位

> 坦诚的开场白：为什么本来不想写、为什么还是要写（1–3 句）。
>
> 交互与具体展示以 Demo 为准，PRD 描述的是业务实体定义、实体关系、以及依赖这些实体运转的业务流程，再加上本期做什么、不做什么。

- 作者：XXX　状态：草稿 v0.x（日期）
- Demo：链接或路径
- 图例：[待确认] = 还没对齐；[提案] = 设计建议，不是已有接口

---

## 1. 需求概述

### 1.1 需求背景
- 上一阶段做到了什么 / 现状的问题（一两段）
- 本期的目标：一句话 + 2–3 个编号目的，每个目的下用 a/b 细化
- 为什么值得做：2–3 条，每条加粗一句论点再解释

### 1.2 产品路线（多阶段项目才需要）
| 阶段 | 核心 | 能力边界 |

### 1.3 基本规则（如有贯穿全产品的规则，如分级、硬线）

### 1.4 用户角色
| 角色 | 典型岗位 | 主要用法 |

### 1.5 User Story
| # | 类型 | 角色 | 用户场景（作为 X，我想……） | 本期 / P0–P3 / Phase N |

### 1.6 分工
| 部分 | 说明 |   ← 不写人名

### 1.7 链接汇总

---

## 2. 各模块详情

### 2.1 优先级
| 模块 | 功能 | 优先级 |

### 2.x 模块名（标题最好直接写出目的，如「订单模块：让用户一眼找到卡住的订单」）
一两句说明这个模块解决什么。

业务实体：XXX
| 字段 | 说明 |   ← 只列关键字段

实体关系：A → B → C（一对多）

业务流程：
1. ……
2. ……

特别注意：
- 边界、约束、容易做错的地方
- 本期先不做什么，放到哪期

### 2.y 本期不做（汇总）

### 2.z 集成架构（技术相关项目才需要，一张简图 + 3–5 条原则）

---

## 3. 前端实现方式（需要给前端团队直接用时才单独成节，保持在原则层面）

---

## 4. 验收标准
以下验收以完整业务流程为单位，每条要端到端跑通才算通过。

### AC-1：一句话描述的业务流程
前提：……
1. ……
2. ……

### 试点指标（可选）
列指标名即可；收益阈值拿到基线后再定，不预写没验证过的数字。

---

## 5. 待确认事项
| # | 问题 |   ← 不写"找谁"

## 6. 愿景 / 后续 Phase 预告（仅供参考，实际以各期 PRD 为准）
```

## 各节写多少

| 章节 | 篇幅 |
|---|---|
| 开场白 | 1–3 句 |
| 需求背景 | 一屏以内 |
| 每个模块 | 一张实体表 + 一段流程 + 3–5 条特别注意 |
| 验收标准 | 5–8 条，每条 3–5 步 |
| 全文 | 大致相当于一个阶段 PRD 的篇幅；超过时先砍细节，不砍边界和验收 |
